# 问题整理文档生成器（problem-doc-creator）

把用户提供的问题梳理文档（Word `.docx`、PDF、Excel 等）作为输入，结合项目代码实际情况，生成一份结构化的问题整理文档。每个问题以列点描述，统一包含六段：**现象 / 代码定位 / 修改范围 / 修改方案 / 测试方案 / 数据修复**。

## 触发条件

- 用户提供 `.docx` / `.pdf` / `.xlsx` 等文档，要求「整理问题列表」「梳理问题」「转成 md 并整理」。
- 用户要求对已有问题清单补充「代码定位 / 修改范围 / 修改方案 / 测试方案 / 数据修复」。
- 用户给出问题描述文字，要求输出结构化问题整理文档。

## 修改范围判定规则（关键，先于一切判定）

项目映射：`LJM=miniapp-finance`（微信小程序）、`LJH=h5-finance`（H5）、`LJW=web-saas`（web 管理端）、`LJS=server-finance`/`server-shared`（服务端与共享层）。

- **LJM / LJH 同步修改**：小程序除「首页(home)」「关注(follow)」外的全部页面均以 H5 承载（LJH 复用 LJW 的 React 技术栈）。凡涉及 LJM 与 LJH 同逻辑的页面/组件/字段，必须**同时修改两处**。
- **LJM / LJW / LJH 同步修改**：若同一逻辑功能在 LJM、LJW、LJH 三端均有对应实现，必须**同步修改三处**。
- **判定方法**：先确认该功能/字段/组件在 LJM / LJH / LJW 中是否均有实现，有则同步改，无则只改实际存在的端。
- **服务端共享层**：逻辑位于 `server-shared` 或 `server-finance` 时，改一处即覆盖所有端（但仍需检查各端是否有独立展示逻辑需同步）。

## 工作流程

1. **读取输入**：
   - `.docx` → 用 python-docx 提取正文与图片（图片提取后链接到 md）。
   - `.pdf` → 用 pdf 解析工具提取文本与图片。
   - `.xlsx` → 用 openpyxl/pandas 读取单元格内容。
   - 图片无法解析时，转用文字描述代替，不阻塞流程。
2. **理解问题**：逐条理解问题现象，明确问题所属的功能模块（视觉 / 标的详情 / 尽调 / 价格分析 / 搜索 / 导出 等）。
3. **代码定位**：用 Grep / SearchCodebase / Read 定位问题对应代码位置（文件 + 行号），记录根因。
4. **判定修改范围**：按上方「修改范围判定规则」判定涉及 LJM / LJH / LJW / LJS 哪些端。
5. **补全方案**：对每个问题补全「修改范围 / 修改方案 / 测试方案 / 数据修复」四段。
6. **生成文档**：按下方「文档结构规范」输出到 `doc/bug/YYYYMMDD/` 目录（与输入文档同目录、同前缀名）。

## 文档结构规范

```markdown
# <主题>问题整理（YYYY-MM-DD）

> 基于原始文档 `<输入文件名>` 梳理，结合当前项目代码实际情况整理。

> **修改规范（强制执行）**：修改时每一条问题都必须调用 `create-auto-fix` 技能。

## 一、<分类 1>
### 1. <问题标题>
- **现象**：……
- **代码定位**：……（文件路径 + 行号，标注根因）
- **修改范围**：……（LJM / LJH / LJW / LJS，标注同步修改要求）
- **修改方案**：……（具体改哪里、怎么改）
- **测试方案**：
  - 需要的 SKILL：`<技能名>`（说明用途）
  - 测试步骤 / 测试标的（含优先级 P0/P1）
- **数据修复**：……（如需重新分析标的某些信息，调用 `patch-item-fields` 技能）

## 问题汇总表
| # | 分类 | 问题 | 严重程度 | 影响范围 |
```

### 六段字段的强制要求

| 字段 | 必须包含内容 |
|------|-------------|
| 现象 | 用户可感知的问题表现，一句话说清 |
| 代码定位 | 具体文件路径 + 行号 + 根因分析 |
| 修改范围 | 明确涉及 LJM / LJH / LJW / LJS 哪些端；标注「LJM/LJH 同步」「LJM/LJW/LJH 同步」等要求 |
| 修改方案 | 具体可执行的改动点，指明改哪个文件哪个函数 |
| 测试方案 | 明确列出做事时需要用到哪些 SKILL 名称，及测试标的（带优先级） |
| 数据修复 | 涉及数据重提取/字段刷新时，指明调用 `patch-item-fields` 技能 |

### 修改时必须遵守（写入文档显式说明）

> **修改时每一条问题都必须调用 `create-auto-fix` 技能**（用该问题的描述创建缺陷并全自动修复）。

## 关键技能引用（在文档中按需标注）

| 场景 | 调用的 SKILL |
|------|-------------|
| 重新分析标的的某些信息（字段重提取/刷新） | `patch-item-fields` |
| 修改代码时逐条创建缺陷并自动修复 | `create-auto-fix` |
| 直查/改漉金Core 数据库 | `lj-db-operate` |
| 调用漉金Core 接口 | `lj-api` |
| 溯源相关业务 | `lj-trace-guide` |

## 输出要求

- 输出到输入文档同目录 `doc/bug/YYYYMMDD/`，文件名与输入文档同名（去掉扩展名）+ `问题整理.md`。
- 文档以「问题汇总表」收尾，逐条列举 `# / 分类 / 问题 / 严重程度 / 影响范围`。
- 每个问题的「测试方案」必须写清所需 SKILL 名称，不能只写步骤。
- 每个问题的「修改范围」必须写清涉及哪些端及同步修改要求。
