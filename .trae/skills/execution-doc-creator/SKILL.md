# 执行文档生成器 (Execution Doc Creator)

## 核心概念

**凡要执行代码（增删改文件/字段/接口/配置），先产出「详细执行版」文档——只写契约、清单、边界，不写论证与背景；AI 严格照此文档执行代码修改。**

**目录**: `doc/execution/<YYYY>/<MM>/`

## 调用时机

- 用户要求实现/落地某个设计或方案（改代码）
- 已有 design/solution 设计文档，需要落地成代码修改
- 用户说"按方案实现/落地/执行/开始写代码"
- 大型重构、跨层改动、多文件修改前

## 与 design / solution 的边界（各干各的事）

| skill | 职责 | 是否碰代码 |
|---|---|---|
| design-doc-creator | 纯设计：概念、决策权衡、架构、数据模型关系 | 否 |
| solution-doc-creator | 纯技术方案设计：总体思路、方案取舍、边界约束 | 否 |
| **execution-doc-creator（本）** | 代码执行文档：改哪些文件、字段长啥样、禁止做什么 | **是** |

设计文档只回答"做什么、为什么"；执行文档只回答"改哪里、改成什么样、按什么顺序改"。

## 文档状态生命周期（文件名前缀 = 文档级状态）

文件名前缀随执行进度自动推进，便于扫目录一眼看出进度、中断后定位续做：

| 阶段 | 文件名前缀 | 何时 |
|---|---|---|
| 未处理 | `未处理-<主题>-执行.md` | 文档刚创建，尚未开始改代码 |
| 处理中 | `处理中-<主题>-执行.md` | 开始执行第一个步骤时重命名 |
| 已完成 | `已完成-<主题>-执行.md` | 全部步骤勾选完成时重命名 |

> 改名只影响人类浏览与状态识别，**无任何脚本/流程依赖执行文档文件名**，可放心改名（设计/方案文档同理）。

- **边界条件**：空值、异常、兼容性处理
- **验证方法**：如何确认这一步做对了

## 编写原则（去论证，保契约）

| 原则 | 要求 |
|---|---|
| **契约优先** | 字段/枚举/映射/签名用完整代码块给出，注释标注要点，不留"待定" |
| **清单即动手** | 新增/修改/删除三清单逐文件列出，每行 = 一个可执行动作 |
| **去论证** | 不写"为什么这样设计"的长篇论证，决策理由一句话带过 |
| **去图示** | 不画 mermaid 图，文字+表格+代码块即可（AI 不读图） |
| **边界硬约束** | 禁止事项 + 注意事项是防 AI 踩坑的护栏，必须明确 |
| **量化验收** | 目标与验收用数字/百分比，不用模糊描述 |
| **过渡方案不留** | 已被取代的方案直接删，不写"过渡补丁" |
| **分步可续** | 第 5 章执行步骤拆到"一步一动作一验证"，每步有独立状态，中断后可定位续做 |

## 端 × 角色分析（涉及多端时必填）

涉及多端/多角色时，先读 [subs/project-map.md](subs/project-map.md) 的端与角色全景图，在「涉及端 × 角色」章节声明哪些端/角色涉及、哪些不涉及及原因。

## 禁止事项

❌ 在正文写长篇论证与背景（设计文档才写）
❌ 画 mermaid 图（AI 执行不读图）
❌ 保留已被取代的过渡方案
❌ 字段/签名/映射写"待定"而不给具体值
❌ 清单遗漏任一增删改文件
❌ 执行步骤写"大致改一下"这类含糊描述（必须精确到字段/值/文件/验证）
❌ 跨步骤跳过状态更新（每完成一步立即勾选 `[x]`，防止中断丢进度）

## 注意事项

1. 文档语言与用户提问语言保持一致
2. 文件名格式：`未处理-<主题>-执行.md`，主题用中文；**开始执行改 `处理中-`，全部完成改 `已完成-`**（仅人工约定，无脚本依赖文件名，改名不影响任何流程）
3. 必须先创建目录 `doc/execution/<YYYY>/<MM>/`（如不存在）
4. 创建完成后告知用户存放路径，并确认是否立即照此执行
5. 执行文档是执行依据：开始改代码前先过一遍三清单，不偏离文档范围
6. 中断续做：重新执行前先读第 5 章状态，从第一个 `[ ]` 步骤继续，已完成步骤不重做
