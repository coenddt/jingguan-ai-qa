# 测试用例生成器

## 核心概念

代码变更后生成标准化测试用例文档，确保功能变更可验证、可回溯。存入 `doc/test-case/YYYY/MM/`。

## 调用时机

| 必须调用 | 不需要调用 |
|----------|-----------|
| 新增功能开发完成 | 纯文档/注释变更 |
| 现有功能修改/重构 | 纯样式/UI 视觉效果（无逻辑变更） |
| 功能/模块删除 | 纯配置文件变更（ESLint、Prettier 等） |
| Bug 修复 | 纯依赖升级（package.json 版本号） |

## 目录结构

```
doc/test-case/<YYYY>/<MM>/未处理-<文件名>.md
```

- `<YYYY>`：当前年份（4 位）
- `<MM>`：当前月份（2 位补零）
- `<文件名>`：功能中文名，如 `实名认证功能测试.md`

示例：
- `doc/test-case/2026/07/未处理-实名认证功能测试.md`
- `doc/test-case/2026/07/未处理-标的搜索功能测试.md`

## 测试用例格式

```markdown
## 测试用例 N：<用例标题>

### 开发端
<小程序 / web-saas / 服务器 / 多端>

### 描述
<简要说明该用例测试什么>

### 步骤
① <自动化测试步骤：生成/运行脚本>
② <人工测试步骤：用 xx 账号执行 xx 操作>
③ <下一步操作>
④ <预期结果>

### 目标
<测试通过的标准，简明扼要>
```

### 字段说明

| 字段 | 必填 | 说明 |
|------|------|------|
| 开发端 | 是 | 小程序 / web-saas / 服务器 / 多端（多端时步骤中分别说明） |
| 描述 | 是 | 一句话说明测试场景 |
| 步骤 | 是 | `①` `②` `③` 编号，同时含自动化测试和人工测试 |
| 目标 | 是 | 测试通过的标准 |

## 编写原则

1. **覆盖核心路径与边界**：至少覆盖正常流程 + 一个异常/边界场景
2. **步骤可执行**：每条必须是可执行的明确指令，不出现模糊描述
3. **自动化 + 人工结合**：既含自动化测试（脚本/API），也含人工测试（UI 验证）
4. **账号/数据准备明确**：需特定账号或数据状态时在步骤中说明
5. **一个文件一个功能**：同功能多个用例放同一文件，不同功能分不同文件
6. **简洁务实**：聚焦可验证的测试步骤和目标

## 文档状态生命周期（文件名前缀 = 文档级状态）

文件名前缀随文档进度推进，便于扫目录一眼看出进度、中断后定位续做：

| 阶段 | 文件名前缀 | 何时 |
|---|---|---|
| 未处理 | `未处理-<主题>.md` | 文档刚创建，尚未开始 |
| 处理中 | `处理中-<主题>.md` | 开始处理/编写时重命名 |
| 已完成 | `已完成-<主题>.md` | 全部完成时重命名 |

状态迁移规则：
- 开始处理 → 文件名前缀改 `处理中-`
- 全部完成 → 文件名前缀改 `已完成-`
- 中断续做：重新打开文档，从上次进度继续，已完成内容不重做

> 改名仅人工约定，**无任何脚本/流程依赖文件名**，可放心改名（各文档生成 skill 统一约定）。

## 输出要求

- 文件名格式：`未处理-<功能名称>测试.md`（中文）；开始处理改 `处理中-`，全部完成改 `已完成-`（见「文档状态生命周期」）
- 先创建目录 `doc/test-case/YYYY/MM/`（不存在则创建）
- 创建完成后告知用户文档存放路径
- 文档语言与用户提问语言保持一致

## 禁止事项

❌ 测试用例出现模糊表述（如"检查是否正常"）  
❌ 一个文件写多个无关功能的测试用例  
❌ 只有人工测试步骤没有自动化验证  
❌ 使用中文文件名含特殊符号或空格  

## 注意事项

1. 步骤编号用 `①` `②` `③` 而非数字列表，区分自动化与人工步骤
2. 异常场景至少包含一个：空数据、权限不足、参数错误、网络超时
3. 涉及多端交互的测试，在步骤中明确标注当前操作在哪一端
4. 如果功能涉及数据库变更，在步骤中包含数据验证步骤
