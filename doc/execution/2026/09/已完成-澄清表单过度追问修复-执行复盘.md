# 澄清表单过度追问修复 执行复盘

> 日期：2026-09-06
> 性质：执行复盘文档（改动内容 + 根因分析 + 经验教训）
> 关联文档：`未处理-问数条件不足澄清分支-执行.md`（原始设计）、`经管之星AI问数助手-最终交付文档.md`（基调）

## 核心概念

为提升问数严谨性而增设的「意图门 + 完整度校验」双重追问机制，因判定门槛过低、与既有缺省规则冲突，导致自然语言提问近乎全部被拦截填表，违背项目「自然语言进，结果直观可见」基调；本次按「先查再说，缺省口径兜底」策略放宽门控，恢复可用性。

## 问题现象

| 场景 | 旧行为（修复前） | 新行为（修复后） |
|---|---|---|
| 「北京收入」 | 弹表单追问年份/维度，不出结果 | 按 unit=北京、year=2026 直接出结果 |
| 「看下项目储备」 | 要求勾选全部维度（year/unit/industry/...） | 全量查询出 50 条明细 |
| 「各产品线销售情况」 | 可能追问年份 | 5 条产品线汇总 + 同比 |
| 「整体达成情况」（统计表） | 追问年份 | LLM 按缺省 2026 直接出结果 |
| 闲聊「今天天气怎么样」 | — | 不崩溃、不弹表单（全量兜底） |

**结果**：演示链路从「提问即填表」恢复为「提问即出数」。

## 根因分析：是优化过度，不是重构

### 定性

| 维度 | 说明 |
|---|---|
| 是否重构 | **否**。重构指代码结构调整（拆分、重命名、分层），本次未动结构，是新增功能行为 |
| 是否优化过度 | **是**。为「不输出错误口径结果」这一严谨性目标，叠加了两层拦截，且拦截门槛过低，把「严谨性」置于「可用性」之上 |

### 三层成因

**1. 门控叠加过激（结构层）**

| 门 | 触发时机 | 修复前行为 | 问题 |
|---|---|---|---|
| A 门（意图门） | query_gen 之前 | `need_more_info=true` 即 `return` 弹表单，**不尝试生成查询** | LLM 天然保守，可查问题也被判缺条件 |
| B 门（完整度校验） | query_gen 之后 | 无条件即要求补齐该模型**全部**维度字段；统计表缺 year 也拦 | 全量浏览诉求被强制填表 |

两道门串行叠加，几乎没有问题能直通执行。

**2. 与既有缺省规则自相矛盾（规则层）**

`query_gen.py` 原有规则：「年份缺省取 2026」——查询生成器本身就有缺省兜底能力。
但意图门把「没写年份」当作缺条件追问，完整度校验把统计表缺 year 当作拦截理由。
**左边能兜底，右边不让过。**

**3. 判定逻辑范围过窄（实现层）**

`intent_gate.given_dims()` 只匹配固定字样（`2025年`、`经营单元为`），「北京收入」识别不出 unit 已给，导致重复追问。

### 本质矛盾

| 项目基调 | 原澄清设计 |
|---|---|
| 自然语言进，结果直观可见 | 自然语言进，先填表再说 |
| 演示是生命线，链路必须端到端可演示 | 链路被表单频繁截断 |
| LLM 查询过守卫校验（只读+白名单）即可执行 | 还需过一层「条件是否足够」的主观判定 |

## 改动方案

### 策略：先查再说，缺省口径兜底

```
旧：提问 → A门拦截? 是→弹表单  否→query_gen → B门拦截? 是→弹表单  否→执行
新：提问 → A门(软提示,不拦截) → query_gen(注入缺省hint) → B门(仅统计表缺year) → 执行
         ↓ 拦截时落 AutoFeedback 留痕                       ↓ 拦截时落 AutoFeedback
```

### 改动清单

| 文件 | 改动 |
|---|---|
| `qa_service.py` | A 门降级：`need_more_info` 不再 return，改为落 `AutoFeedback` + 生成 hint 继续查询；B 门前移至执行前，仅统计表缺 year 才拦 |
| `query_clarify.py` | `missing_dims` 删除「无条件=缺全部维度」分支，只保留统计表缺 year；新增 `build_query_hint()` |
| `intent_gate.py` | 判定基准从宽：缺年份/缺维度不算条件不足，只有完全无法对应数据表才拦截；开 `reasoning=disabled` 降延迟 |
| `query_gen.py` | 支持注入 `hint`（追加 user 消息尾部，system 前缀恒定不影响预热缓存） |
| `query_candidate.py` | `generate_candidates` 透传 `hint` |
| `conclusion.py` | 空结果时如实说明口径 + 给调整条件的文字追问（不弹表单） |
| `ClarifyForm.tsx` | 新增「按默认（2026年）直接查」跳过按钮 |

**A 门降级（qa_service.py）**

**B 门收紧（query_clarify.py）**

```python
def missing_dims(query: dict) -> list[str]:
    model = query.get('model')
    cond = query.get('condition') or {}
    topic_keys = {k for k in cond if not k.startswith('$')}
    # 仅统计表缺年份才拦截；其余一律放行（全量/空结果由结论层承接）
    if model in _REQUIRED_YEAR_MODELS and 'year' not in topic_keys:
        return ['year']
    return []
```

## 经验教训

1. **严谨性不能以可用性为代价**：数据问答的核心价值是「能问出结果」，而非「问不出错结果」。宁可给出口径可调整的结果，也不要把用户挡在表单外。

2. **兜底能力优先于拦截能力**：当系统已有缺省兜底规则（如年份默认 2026）时，新增拦截门必须先确认「兜底是否已覆盖该场景」，否则就是重复造墙。

3. **门控必须有逃逸通道**：任何拦截用户的门（表单、确认框）都必须提供「跳过/用默认值」按钮，否则就是死锁。本次前端补了「按默认直接查」。

4. **告警闭环是门控的必需品**：放宽门控不等于放弃防护——被策略放行的拦截必须落 `AutoFeedback`，通过告警频率回溯 prompt 或规则是否需要调整。本次 A/B 门拦截均落反馈。

5. **最小 diff 原则**：修复时优先改判定逻辑（收紧门槛），而非删除整个机制。澄清表单作为统计表口径不明的兜底仍然保留，只是不再滥用。

## 禁止事项

❌ 禁止把「条件不足」拦截置于「缺省兜底」之前
❌ 禁止拦截门不提供跳过/默认值通道
❌ 禁止拦截触发后不落 AutoFeedback 静默失守
❌ 禁止为严谨性牺牲演示链路可用性

## 注意事项

1. **后续若需收紧**：通过 `AutoFeedback` 告警频率判断，而非主观调高判定门槛
2. **闲聊识别待优化**：当前闲聊会返回全量数据（不崩溃），后续可在 `query_gen` 加闲聊检测返回友好提示
3. **统计表缺年份仍会追问**：这是有意保留的硬门（口径不明），但用户可点「按默认 2026 直接查」跳过
4. **缓存命中路径不受影响**：`exact_cache` 复用历史已验证模板，不套 A/B 门
