# 问数慢查询：补分步耗时日志 + 多候选查询并发生成择优

## Context（为什么做）
智能问数链路（`qa_service.ask_stream`）是一条流水线：`LLM生成查询 → 守卫校验 → Mongo取数 → LLM生成结论`。
每个自然语言问题**至少 2 次串行 LLM 调用**；守卫校验失败会再**串行回传 LLM 重试（retries=3）**，
最坏 = 1 首轮 + 3 重试 = 4 次串行 LLM + 多次取数 = 十几秒。这是"查询有时特别慢"的主因。

但目前**没有分步耗时日志、没有 requestId 关联**，`meta` 只存总时长 `elapsed_s`，
无法从事实定位慢点。因此本计划分两阶段：
- **阶段一**：补 requestId + 分步耗时日志（先锁定慢点，用事实验证分析）。
- **阶段二**：多候选查询并发生成 + 择优（把"verify 失败的串行重试"换成"并行候选择优"）。
- 部署到服务器（<user> 账号 pm2）后做针对性测试，用日志印证假设；成立后再考虑后续优化。

## 现状要点（已确认）
- `StepTracker`（`server/app/agent/step_tracker.py`）已逐步骤记录 `ts`/`elapsed`，`out()` 含每步耗时；
  `resp['steps']` 已随 SSE done/落库到 `aiMeta`——**数据已存在，只是没有被日志打点、无 requestId 关联**。
- `query_guard.verify()` 是**纯本地同步快校验**（`server/app/services/query_guard.py`），适合并发候选逐一校验。
- `query_executor.run()` 内部会再 `verify` 一次；`EXEC_TIMEOUT` 取数超时（`query_policy.py`）。
- `llm_client.invoke()` 每次返回 `ret['elapsed_s']`、`total_tokens`（`server/app/services/llm_client.py`）。
- `/api/qa/ask` 路由**无认证依赖**（`server/app/routers/qa.py`），可 curl 直测；服务监听 `127.0.0.1:8000`（`server/process.json` pm2 名 `jingguan-api`）。
- 约束：`agent/` 须纯函数（本计划不打点子放 agent，打点在 service 层 `qa_service`）；依赖只向下；
  配置只在 `config/__init__.py` 统一出口。

## 阶段一：分步耗时日志 + requestId

### 1. 新增 `server/app/log.py`（日志与 requestId 基建，单一职责）
- `ContextVar` `_request_id` + `get_request_id()` / `bind_request_id()`。
- `configure_logging()`：stdlib `logging`，输出到 stdout（pm2 可捕获），统一格式含 `req=<requestId>`。
- `request_id_middleware(request, call_next)`：取请求头 `X-Request-Id` 或 uuid4 短码，绑定 contextvar，
  记录请求开始/结束（method/path/status/latency_ms），并把 requestId 回写响应头。
- 提供 `log(level, msg, **fields)`，自动把当前 requestId 并入每条日志。

### 2. `server/app/main.py`
- 应用启动前 `configure_logging()`；注册 request 中间件（dispatch 逻辑引用 `log.py`，main 只做组装）。

### 3. `server/app/services/qa_service.py`（打点，不动业务逻辑）
- 请求开始记 `ask_start`；**每步 done 后记 `ask_step {index,title,elapsed_ms,desc}`**。
- 每次 LLM 调用（query_gen / conclusion / 重试修正）记 `llm_call {scenario,elapsed_s,tokens}`。
- 守卫失败重试记 `ask_retry {attempt,error}`。
- 结束时记 `ask_done {total_ms,retries,row_count}`。
- `resp['meta']` 追加 `request_id`（落库 aiMeta，便于 DB 侧关联）。

> 分步数据本来就在 `aiMeta.steps`，本阶段只是把它变成**可见的日志流** + requestId 关联，
> 供部署后 `pm2 logs` 直接按 req 串联看每步毫秒。

## 阶段二：多候选查询并发生成 + 择优

### 4. 新增 `server/app/services/query_candidate.py`（单一职责）
- `async generate_candidates(question, few_shots, model_conf, n, concurrency)`：
  - 用 `asyncio.Semaphore(concurrency)` + `asyncio.gather` 并行发起 `n` 次 `llm_client.invoke('query_gen', ...)`。
  - 多样性：候选 0 带 few_shots，其余不带（或错位切分 few_shots），避免同 prompt 同质。
  - 返回原始 query 列表（未校验）。
- `pick_checked(candidates) -> (list[checked], list[{idx,status,error}])`：
  - 逐一 `query_guard.verify()`，返回"通过守卫的有序 checked 列表" + 每候选状态（过/GuardError），供日志。

### 5. `server/app/services/qa_service.py` 改造 step1/step2 区域（`L154-L182`）
- 原"串行 1 条查询 + verify 失败回传 LLM 重试"改为：
  1. `generate_candidates(...)`（并行 N 条）；
  2. `pick_checked(...)` 取全部过关候选（本地快校验）；
  3. **按序尝试执行**：对每个过关候选 `query_executor.run()`，成功即用；失败记日志后试下一个（**无需再调 LLM**）；
  4. 若全部候选都失败 → **保留原串行错误回传重试循环作为最后兜底**（行为优雅降级，不破坏正确性）。
- step1 desc 注明"生成 N 个候选并择优"；`retries`/候选状态写入日志与 meta。
- SSE 事件结构、步骤序号（1=生成查询、2=安全校验、3=执行取数、4=生成结论）保持不变，前端无需改动。

### 6. 配置（`server/app/config/qa.py` + `__init__.py` 导出）
- `QA_QUERY_CANDIDATES = 3`（候选数）
- `QA_QUERY_CANDIDATE_CONCURRENCY = 3`（并发上限，防 LLM 供应商限流）

## 验证（严格按 testing-rules：本地仅静态自检，常驻只在 <user> 服务器 pm2）

### 阶段一自检（本地）
- 对每个改动文件：`python -m py_compile <file>` + `python -c "import <模块>"` 确认无导入错。
- 服务器无关，不部署前后端分离验证，仅确认模块可加载。

### 部署（阶段一）
1. 远端侦察（免密 `ssh-server-task`）：`pm2 list` + `pm2 describe jingguan-api` 拿**真实部署根目录**（可能 `/home/<user>/jingguan/api` 或 `/home/<user>/server`，以实际为准）。
2. 按 deploy-rules 先比对版本防漂移：远端 `grep -n <关键标识> <远程 py>`。
3. SCP 上传阶段一改动文件到真实部署根对应路径。
4. `pm2 restart jingguan-api`；`pm2 logs jingguan-api --lines 30 --nostream` 确认启动无报错。

### 针对性测试 + 印证（阶段一，全部经 ssh 在服务器 `curl http://127.0.0.1:8000`）
- 测试题覆盖不同分支（无需认证）：
  - 命中精确缓存：重复第三方一次已问过的问题 → 预期快、query_source=exact_cache。
  - 全新聚合题：`北京代表处今年达成情况` → 走 ReportOverall+GoalLedger，见证 step1/step4 两次 LLM 耗时。
  - 明细类：`政企行业收入3000万-5000万数据` → query mode 路径。
- 印证方式：`pm2 logs` 按 `req=` 串联，看每步 `elapsed_ms`。**预期**：
  LLM 步骤（1、4）占大部分秒级，执行取数（3）次之且通常 <1s，验证`串行 LLM×次数`为慢点主因。
- 中间决策点：若日志印证"慢点=串行 LLM 次数/重试"，则继续阶段二；若与假设不符，**停下并向用户说明**，不硬推阶段二。

### 阶段二自检 + 部署 + 验证
- 同阶段一：py_compile/import；SCP 上传 `query_candidate.py`+`qa_service.py`+`config` 俩文件；`pm2 restart`。
- 针对性测试：用会触发守卫失败的刁钻问题，看日志中**候选数/每候选校验状态/首次执行成功即停**，
  对比改造前后 `done.total_ms`（尤其坏 case 应从"4×LLM"降至约"1×并发波 +1次执行"）。
- 回归：正常聚合/明细/缓存命中题在阶段二下仍正常渲染卡片（前端无感知，SSE 协议未变）。
