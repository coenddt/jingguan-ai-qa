# 问数查询链路优化：分步日志 → 多候选择优 → 热度分级 + 前缀预热

## 核心概念

慢点的根源是**串行 LLM 调用**：生成查询 + 生成结论各一次、秒级耗时，校验失败还会整轮重试。
治理路线 = 用日志锁死慢点 → 并行候选择优 → 按缓存热度控制生成开销 → 前缀预热摊薄成本。

**设计红线**：text-to-query 产物一律先过守卫再执行；模糊命中只作 few-shot、绝不直接执行；缓存复用必过守卫。

## 阶段一：分步耗时日志（锁定慢点）

新增 `server/app/log.py`（requestId 注入 + 结构化日志），`qa_service` 全链路打点。

```python
# app/log.py —— 事件格式（结构化，requestId 贯穿）
log('info', 'llm_call', scenario='conclusion', elapsed_s=5.0, tokens=593)
log('info', 'ask_done', total_ms=8657, retries=0, query_source='llm')
```

| 步骤 | 实测耗时 | 结论 |
|------|----------|------|
| 理解问题 / 取数 | 毫秒级 | 非慢点 |
| **生成查询 query_gen** | 冷 1.5~5s | 慢点（命中缓存可到 1.5s） |
| **生成结论 conclusion** | ~5s | 慢点（单次最长） |
| 校验失败串行重试 | 成倍增加 | 慢点放大器 |

## 阶段二：多候选并发生成择优

新增 `server/app/services/query_candidate.py`，并行生成 N 个候选，本地守卫校验后首过即执行。

```python
cands, prime = await query_candidate.generate_candidates(
    question, few, model_conf, n_cands, conc, preheat=bool(QA_PREHEAT_ENABLED))
checked_list, statuses = query_candidate.pick_checked(cands)  # 守卫全检，快
```

| 方式 | 校验失败时 | LLM 调用 | 并发风险 |
|------|-----------|----------|----------|
| 原串行重试 | 整轮回传 LLM 重试（倍增耗时） | 多轮串行 | 无 |
| 并行候选择优 | 本地另取下一候选，**不回传** | 一次并行 N | 并发上限限制 |

- `sem` 信号量钳制并发上限，防供应商限流。
- 候选 0 带 few_shots、其余不带，维持多样性。

## 阶段三：缓存热度分级 + 前缀预热

`server/app/config/qa.py` 按 best fuzzy score 分级候选数/并发。

```python
# 分级：exact 极致省 / warm 低开销 / cold 候选兜底
QA_TIER = {
    'exact': {'candidates': 0, 'concurrency': 0},
    'warm':  {'candidates': 1, 'concurrency': 1},
    'cold':  {'candidates': 3, 'concurrency': 2},
}
QA_HOT_FUZZY_SCORE = 0.75   # best_score >= 此值 → warm
QA_PREHEAT_ENABLED = True   # 与候选并发预热共享 system 前缀
```

- `tier=exact`：0 候选，直接复用模板，**省一次 query_gen**。
- `tier=warm`：1 候选，有近例可依，低开销。
- `tier=cold`：3 候选但并发收窄为 2，防限流降成本。

**前缀预热**（漉金Core 思路迁移）：query_gen 的 system 前缀对所有问法恒定，把它随候选并发打进 LLM 缓存，命中即按缓存价计费。`llm_client` 捕获 `prompt_cache_hit_tokens`，日志实证命中。

## 实测效果对比

| 场景 | 优化前 | 优化后 | 营收点 |
|------|--------|--------|--------|
| 冷问（tier=cold） | 3 并发生成 + 结论 | 同量并行、前缀缓存 | 3 候选 `cache_hit=8064`（3×2688 共享前缀） |
| 重复问（tier=exact） | 再造一次 query_gen | 0 生成 | 总耗时 8657→**3882ms** |
| 近义问（tier=warm） | 3 候选冗余 | 1 候选即过守卫 | 候选生成成本约减 2/3 |
| conclusion | 无前缀可cache | 部分命中 | `cache_hit=128/384` 递增 |

## 部署与回滚

- 部署：改动文件 `scp` 到 `/home/<user>/jingguan/api`（服务端 `<user>` 账号 pm2 管理）。
- 回滚：还原 `qa_service.py` / `query_candidate.py` / `config/qa.py` 即可，`QA_PREHEAT_ENABLED=False` 可单独关预热。

## 禁止事项

❌ 禁止模糊命中直接执行（只作 few-shot）  
❌ 禁止跳过守卫复用来路模板  
❌ 禁止把关预热请求做到关键路径上（与候选并发）  
❌ 禁止把并发上限调高到引发供应商限流  

## 注意事项

1. 结论生成是单次最长步骤（~5s），可另开任务做低成本模型/降采样，本次不做。
2. 精确命中分级降耗时显著，但前提是缓存命中率高、守卫不放过异常模板。
3. 前缀预热依赖供应商支持 prompt 前缀缓存；不支持时 `cache_hit` 恒 0，不影响主流程。
4. 候选并发成本与收益需按平台 rate 权衡，阈值（0.75）可在 config 单独调。
