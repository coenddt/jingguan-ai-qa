## 测试用例 3：AutoFeedback 写入链路端到端 ✅

### 开发端
服务器

### 描述
验证载体 schema 注册、索引/归档集合、internal 写入、默认值补全、删除归档全链路可用。

### 步骤
① 服务器 `.venv/bin/python` 内执行：`register_all()` + `await connect()` 初始化 store
② `await store.run_as_internal(_ins)` 插入一条测试记录（category=guard, triggerPoint=verify_test，不传 userName）
③ 用 GQL 按 `_id` 读回，打印 `_id/category/triggerPoint/reason/userName`
④ `await store.run_as_internal(_rm)` 删除该记录，打印 deletedCount / archivedCount
⑤ 断言：写生成为 `AF` 前缀 `_id`；读回 `userName=='系统'`（默认值补全）；`archivedCount>=1`（归档集合可用）

### 目标
写→读→删全链成功且往返一致；`AF` 前缀 _id 生成；default 补全；`<collection>_deleted` 归档生效。

## 测试用例 4：run_as_internal 异步协程契约 ✅

### 开发端
服务器

### 描述
验证写入必须传 `async def` 可调用；传 `lambda` 返回协程会导致 insert 不落库（回归保护）。

### 步骤
① 复现旧写法：`run_as_internal(lambda: store.insert(...))`，观察是否返回未 await 协程
② 采用新写法：定义 `async def _write(): return await store.insert(...)`，`await run_as_internal(_write)`
③ 断言：旧写法报 `coroutine object is not subscriptable`（或 insert 未生效）；新写法成功 `INSERTED`
④ 删除测试记录

### 目标
新写法（async 内层函数）写入链路成功；旧写法被拦截暴露，防止回退。

## 注意事项

1. 用例 5 为静态审阅：真实触发需 LLM 产出越界查询或缓存模板被污染，运行期难以稳定复现，以链路验证（用例 3）+ 代码审阅代偿
2. 测试脚本含服务器连接信息，执行后必须删除（本计划已列，见用例 6 ②）
3. 写入验证必须走 `run_as_internal` + async 内层函数，直写 store 无法覆盖权限路径
